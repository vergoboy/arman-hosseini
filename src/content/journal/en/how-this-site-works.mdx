arman-hosseini.ir is the personal site of Arman Hosseini: a static, bilingual site generated by Astro, with a small SEO/AEO layer, a zero-dependency Node admin service, and an Obsidian publishing pipeline that turns Markdown and MDX notes into atomic releases.

## What is arman-hosseini.ir?

It is a personal portfolio and journal published in English and Persian (RTL). The build output is plain HTML, CSS and a little JavaScript; there is no application server for visitors. Alongside the public site, a separate admin service lets the author edit SEO fields, manage media and approve pages coming from Obsidian.

## Why is the site static?

Static HTML is the fastest thing a server can send, is cheap to host, and gives both search engines and AI answer engines complete, parseable pages. Astro compiles every route to HTML at build time, so a request is served straight from nginx with no per-request rendering.

The only client-side JavaScript is a few lines for the theme toggle and a privacy-friendly page-view beacon that the admin service records through a `POST /api/v` endpoint.

## How is the project structured?

The project has four layers:

1. **Presentation** — Astro routes in `src/pages/` render the home, about, projects, journal, tags and contact pages, plus `404`, RSS, `sitemap.xml`, `robots.txt`, `llms.txt` and the web manifest.
2. **Content** — Markdown and MDX files in `src/content/{projects,journal}/{en,fa}`, validated by the schema in `src/content.config.ts`. Dashboard edits are stored separately in `content-meta/overrides.json`.
3. **SEO/AEO** — `src/lib/seo.ts` turns each entry into page metadata, an Open Graph/Twitter card and JSON-LD.
4. **Admin and deploy** — the service in `admin/` manages content and builds new releases, which `deploy/` serves through nginx.

```
Obsidian ─Vergo MDX Studio─► /api/studio ─► Inbox ─(approve)─► src/content ─► astro build ─► releases/<ts> ─► current (symlink)
Dashboard (/admin) ─► content-meta/overrides.json ─► same build
```

## How are pages generated?

Astro content collections load `src/content/projects/**` and `src/content/journal/**`, and the schema in `src/content.config.ts` defines the frontmatter. The collection id is derived from the file path with the extension stripped, so `en/foo` and `fa/foo` never collide.

Every entry shares the same base frontmatter — `title, date, lang, tags, summary, draft` — plus optional SEO fields such as `seoTitle`, `seoDescription`, `keywords`, `image`, `imageAlt`, `schemaType`, `noindex`, `canonical`, `updated` and `faq`. Drafts are skipped during the build unless a dashboard override changes their status.

```yaml
---
title: "Example entry"
date: "2026-10-08"
lang: "en"
summary: "One-sentence answer shown as the quick-answer block."
tags: ["Astro"]
draft: false
---
```

## How does the SEO/AEO layer work?

Each page carries its own title, description, keywords, canonical URL and optional `noindex`. `src/lib/seo.ts` builds the Open Graph and Twitter metadata, plus a JSON-LD `@graph` that includes the site's `Person` entity and the page node selected by `schemaType` (`Article`, `TechArticle`, `HowTo`, `FAQPage`, `SoftwareApplication` and others).

The build also emits machine-readable companions: `sitemap.xml` with hreflang alternates and `lastmod`, `robots.txt` that allows AI crawlers, `llms.txt`, per-language RSS feeds and a web manifest. A short "quick answer" block is rendered from each entry's `summary`, and any frontmatter `faq` entries become a visible FAQ section with matching structured data.

## How does the admin dashboard work?

`admin/server.mjs` is a Node HTTP server with no npm dependencies. It exposes a fixed route table; sensitive routes require a session, and every write requires a CSRF header. Authentication uses a scrypt password hash, a HttpOnly `SameSite=Strict` session cookie, a login rate limit and a strict Content-Security-Policy.

The dashboard is a small static app served under `/admin/`. It lists pages with filters and bulk actions, edits per-page SEO with a live preview, manages a media library, links translations, toggles draft/disabled status with undo, shows analytics and build logs, and supports one-click rollback. Each page carries a **live check**: the dashboard confirms whether the page is present in the current release and whether the public URL actually answers. All dashboard edits are written to `content-meta/overrides.json` (keyed `collection/lang/slug` or `static/<lang>/<page>`) rather than into the content file, so re-publishing a note from Obsidian never erases an SEO tweak.

## How does the Obsidian publishing pipeline work?

The companion plugin, Vergo MDX Studio, lets the author write MDX in Obsidian, preview it with the site's own CSS, and send the compiled page plus its images and videos to the admin service.

The plugin authenticates with a revocable bearer token against the `/api/studio/` endpoints. Media is staged and must match its SHA-256-derived name. Every page must compile and obey the site's MDX rules — built-in components only, no imports or exports, no server-side APIs — and a broken page is rejected with the file and line number. Valid pages land in the dashboard inbox and nothing goes live until it is approved.

## How are releases deployed?

When a build is started, the admin service runs the project build command into a fresh directory under `releases/<timestamp>`. Only after the build succeeds does it switch the `current` symlink that nginx serves, keeping the last five releases. A failed build can never take the site down, and rollback is a single action.

## What MDX components are built in?

Every MDX page gets six built-in components — `Callout`, `Card`, `Tabs`/`Tab`, `YouTube`, `AudioPlayer` and `VideoPlayer` — and can use them directly with **no `import`**. They are registered in `src/lib/mdx-components.ts` and injected into every entry by `EntryPage.astro`.

## What is not allowed in MDX pages?

The admin service validates every Obsidian submission *and* every dashboard edit against a small policy, rejecting the page with a file, line and column on any violation:

- **Only the built-in components** — any other `<Component>` name is rejected.
- **No imports** — pages need nothing beyond the built-ins.
- **No `export`** and **no server-side APIs** (`process`, `require`, `fetch`, `import()`, …) — MDX is compiled on the server.
- **Code inside fenced blocks is ignored** by the rules, so examples like `import x from "y"` are fine to show.

This is defence in depth, not a sandbox — every page still passes through a human approval. And because the site is static, there is no React and no client-side interactivity in content, so runtime handlers like `onClick` are not available.

## What are the limitations?

- **No client framework.** Content cannot rely on browser-side interactivity; pages are HTML.
- **Translations need a link.** An English and Persian page get hreflang and the language switcher only when they share a `translationKey`.
- **Single operator.** The admin service is built for one author with one password and a local data directory, not for multi-user hosting.
